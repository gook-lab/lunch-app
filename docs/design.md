# lunch-app 설계 노트

이 문서는 lunch-app의 구조적 결정과 그 이유를 기록합니다. 앱을 돌리는 방법은 README를 참고합니다.

## 스택 — 선택과 이유

| 선택 | 이유 |
|---|---|
| Vite + React + TS | 정적 SPA 하나, 서버 없음 |
| Firebase Firestore | 서버 없이 쓰는 공유 저장소 |
| Firebase 익명 로그인 | 로그인 화면 없이 규칙에서 `request.auth` 사용 |
| MODUL `@gook-lab/ui` | 버튼·시트·모달·태그 재사용, 직접 만든 UI 는 게임판·로드맵·지도 핀뿐 |
| 카카오맵 JS SDK | 좌표·키워드 검색, REST 키 미사용 |

## 카카오 도메인 등록 — 접속 주소마다 한 줄

플랫폼 웹 도메인에 **배포 도메인(공개 데모·팀용) + 로컬 개발 주소**만 등록합니다.
와일드카드 서브도메인은 비즈 앱에서만 되고 도메인은 최대 9개라, Vercel PR 프리뷰 URL은 사전 등록이 불가능합니다. 그래서 **PR 프리뷰 배포를 쓰지 않습니다.**

등록하지 않은 origin 에서는 SDK 스크립트 자체가 401 로 떨어집니다.

```
{"errorType":"AccessDeniedError","message":"domain mismatched! caller=http://localhost:5173. check out registered web domains."}
```

개발 서버에서는 지도 탭이 이 원인과 등록할 주소를 화면에 적어 줍니다. 배포 화면에서는 환경변수·콘솔 경로 대신 사용자용 안내만 보여 줍니다(`import.meta.env.DEV`). 개발 서버 포트를 바꾸면 그 포트도 등록해야 합니다.

## 데이터 구현 — Firebase(팀용) · 브라우저 저장(공개 데모)

`src/services/lunch.ts` 와 `predictions.ts` 는 진입점이며, 빌드 타임 `VITE_DEMO` 플래그로 `*.firebase.ts` 또는 `*.demo.ts` 를 선택합니다. 조건문이 코드에 인라인으로 작성되어 번들러가 쓰지 않는 쪽을 떨어뜨리므로, 공개 데모 빌드는 Firebase SDK 를 포함하지 않고 팀용 빌드는 Firebase 를 나중 청크로 로딩합니다. 메인 번들 크기가 912KB 에서 374KB 로 줄어듭니다(2026-10-13 에 `vite build` 로 측정).

공개 데모는 서울시청 주변의 가상 식당을 localStorage 에 저장합니다(`services/demoStore.ts`). 이렇게 공개 데모는 실제 사무실 위치를 노출하지 않고 방문 기록도 남기지 않습니다.

## 구조 — 깨면 재발하는 계약

### 날짜 기준 — KST 고정 · 앱과 규칙 두 구현

`visits` 문서 id 가 `YYYYMMDD` 입니다. 기기 시계를 따라가면 노트북을 UTC 로 둔 사람이 오전 9시에 "어제" 문서를 열고, 같은 날 문서가 두 개 생깁니다.

클라이언트는 `src/lib/date.ts` 의 `todayKST()`, 규칙은 `firestore.rules` 의 `isTodayKST()` 입니다. **규칙은 이 JS 를 쓸 수 없습니다** — 규칙 언어에 타임존 변환도 zero-pad 포맷도 없고 `request.time.year()` 는 항상 UTC입니다. 구현은 둘, 계약은 하나이고, 그 계약을 지키는 것은 `pnpm test:rules` 입니다.

### 후보 산출 — 순수 모듈 단일 경로

`src/lib/candidates.ts` 의 `selectCandidates()` 가 순수 함수로 정합니다. 돌림판은 넘겨받은 당첨 index 로 회전만 합니다. 반환은 **단계별 카운트**입니다 — `afterCategoryCount` 가 "N곳 중", `recentlyVisitedCount` 가 "M곳은 최근에 갔습니다". 이 둘을 헷갈리면 화면 숫자가 실제와 어긋나는데, 그 문구가 이 앱의 유일한 공정성 장치입니다.

### onSnapshot 순서 — 익명 로그인 완료 후 구독

`onSnapshot` 의 `permission-denied` 는 재시도 없이 리스너를 영구 종료시킵니다. 익명 로그인이 붙기 전에 구독하면 **신규 기기에서만** 조용히 실패하고, 캐시된 uid 가 있는 기존 기기에서는 재현되지 않습니다. `src/services/lunch.firebase.ts` 의 `subscribeToday()` 가 `ensureAuth()` 를 기다리는 이유입니다. 로그인이 실패하면 `ensureAuth()` 는 결과를 버려, "다시 시도" 가 익명 로그인을 처음부터 다시 보냅니다.

탭을 켜둔 채 자정을 넘기는 경우도 같은 급의 문제라, `useTodayKST()` 가 `visibilitychange`·`focus`·1분 타이머로 날짜를 다시 잽니다.

### 규칙의 한계 — 집계·문서 수 상한 미지원

**문서 수 상한은 구현하지 않았습니다.** Firestore 규칙에는 집계·카운트가 없습니다. 막았다고 적어두면 아무도 다시 보지 않으므로, 못 한다고 적어 둡니다. 8명 사내 링크에서는 목록이 이상하게 불어나면 사람이 바로 보고, 삭제 금지가 복구를 보장합니다.

`auth != null` 은 "링크를 아는 누구나" 와 동치입니다. 접근 통제가 아니라 기기당 신원을 만들어 필드 검사를 가능하게 하는 장치입니다.

### places 수명주기 — 삭제 금지 · 수정과 active 토글

`visits` 가 `placeId` 를 참조하므로 삭제는 막혀 있습니다. 대신 `name`·`lat`·`lng`·`walkMin`·`category` 수정을 연습니다. 잠가 두면 좌표를 잘못 고른 가게가 `walkMin` 탓에 영원히 후보에서 빠지고, 고칠 길이 없어 풀 크기가 오염됩니다.

좌표를 고치면 `walkMin` 을 같이 재계산해서 씁니다. 따로 두면 둘이 어긋납니다. 카테고리는 넣을 때도 고칠 때도 같은 칩(`CATEGORIES`)으로만 고릅니다. 글자로 받으면 목록에 없는 카테고리가 들어가 로드맵 조각과 필터에서 빠집니다.

### 별점 — 사람마다 한 표 · 평균은 화면에서

별점은 `places/{placeId}/ratings/{익명 uid}` 에 사람마다 한 표로 둡니다. 처음에는 가게 문서의 `rating` 하나를 마지막에 고친 사람이 덮어썼는데, 여럿이 쓰는 앱에서는 평균이 아니라 마지막 의견만 남았습니다. 목록·지도·결과가 모든 가게 평균을 보여야 하므로 컬렉션 그룹(`ratings`) 하나를 구독하고 `lib/ratings.ts` 의 `summarizeRatings()` 가 가게별 평균·인원·내 표를 냅니다. 가게 문서에 남아 있던 예전 별점은 "예전 별점" 한 표로 셉니다.

규칙은 자기 uid 문서만 쓰고 지우게 하고, 점수는 1~5 정수, 한줄평 40자, 이름 12자, 시각은 서버 시각만 받습니다(`firestore-rules.test.ts` S1~S4). 별점은 고르는 데 참고만 하고 후보 산출과 당첨에는 쓰지 않습니다.

## 화면 구성 — 오늘 · 목록 · 지도 세 탭

휴대폰은 하단 탭 바, 960px 부터는 머리말 안의 탭 묶음입니다.

- **오늘**: 게임 무대가 먼저, 조건(로드맵)이 아래(데스크톱은 오른쪽)에 옵니다. 게임이 끝나면 결과 티켓이 모달로 뜨고, 닫으면 게임 아래엔 가게 이름·도보 분과 "결과 보기"·"다시 뽑기" 한 줄만 남습니다 — 티켓 전체가 남으면 모달과 같은 카드가 화면 아래를 계속 차지했습니다. 티켓 머리말은 "🎱 핀볼로 뽑은 오늘의 점심" 처럼 방금 한 게임을 적습니다. 결정한 뒤와 "오늘 정한 곳" 배너에는 "동료에게 알리기" 가 있습니다(휴대폰 공유 시트, 아니면 클립보드).
- **목록**: 맨 위에 최근 다녀온 곳 5번, 그 아래 후보에 들어가는 가게와 접힌 "꺼 둔 가게". 줄마다 "지도" 단추가 지도 탭을 그 핀을 고른 채로 연습니다.
- **지도**: 회사 위치 카드(GPS · 지도 찍기 · 지도 가운데로), 가게 검색, 지도. 데스크톱은 지도 | 오른쪽 칸 두 칸입니다. 고른 가게 카드·결과 티켓(결정 뒤)·"오늘 정한 곳" 배너에 "길찾기" 가 있습니다 — 회사에서 그 가게까지 카카오맵 도보 경로를 새 탭으로 연습니다(`lib/directions.ts`, 키 불필요).

로드맵은 반지름이 도보시간, 각도가 카테고리인 그림이고, 링과 조각이 그대로 필터 컨트롤입니다. 실제 위경도가 아닙니다 — 이 그림이 답할 질문은 "어디 있나" 가 아니라 "지금 필터에서 무엇이 후보이고 무엇이 왜 빠졌나" 입니다. 진짜 좌표는 지도 탭이 맡습니다.

점은 다섯 처지로 그립니다. **후보 / 다시 넣음 / 최근 제외 / 조건 밖 / 꺼짐**. 특히 "다시 넣음"(released)을 후보와 구분해서 그립니다. 최소 5곳을 채우려고 최근 방문을 도로 꺼낸 것이라, 그냥 후보로 그리면 화면이 "최근 1주 제외" 를 지킨 것처럼 보입니다. 이 앱이 내세우는 공정성 장치가 그 한 가지뿐입니다.

반지름은 제곱근 눈금입니다(0분 32 → 15분 150, 5분 링이 100). 점심 가게는 대부분 5분 안이라 직선 눈금에선 사무실 앞에 점과 이름이 몰렸습니다. 같은 조각 안에서는 이름이 붙는 점(후보·다시 넣음·최근 제외)끼리 각도를 최대한 벌리고, 이름표는 아래 → 위 → 오른쪽 → 왼쪽 순으로 "사무실" 글자·링 알약·다른 이름표를 피해 자리를 찾습니다. 범례는 이름이 붙는 세 처지만 적습니다.

## 톤앤매너 — 신문 편집물 같은 점심 오락실

화면은 종이 질감, 굵은 제목, 제한된 빨강·주황 강조색을 쓰는 **복고풍 신문 편집물**과 짧은 게임 한 판의 **점심 오락실**을 결합합니다. 장식은 즐거움을 더하는 범위에서 쓰고, 사용자가 결정을 내려야 하는 문장과 오류 안내는 장식보다 뜻이 먼저 읽혀야 합니다.

- **목소리**: 친근한 해요체로 짧게 말합니다. “돌리고, 정해요”, “여기로 결정”처럼 사용자가 지금 할 행동을 먼저 씁니다.
- **게임과 업무의 경계**: 게임 이름·장면 설명에는 익살과 긴장감을 허용합니다. 후보 조건·확률·방문 기록·오류에는 농담을 섞지 않고 사실과 다음 행동을 함께 적습니다.
- **용어**: `가게`, `고를 가게`, `뽑힌 곳`, `결정`, `다시 뽑기`를 기준어로 씁니다. 같은 행동을 화면마다 `다시 하기`·`재시도`처럼 바꿔 부르지 않습니다.
- **문장 구조**: 제목은 결과나 상태, 본문은 이유, 단추는 다음 행동으로 나눕니다. 개발 키·콘솔·도메인 같은 운영 정보는 사용자 화면에 노출하지 않습니다.
- **색과 계층**: 빨강은 현재 선택과 핵심 실행, 주황은 보조 강조와 회복 행동에 씁니다. 모든 카드가 경쟁하지 않도록 한 화면의 가장 강한 행동은 하나만 둡니다.
- **모바일 원칙**: 자주 쓰는 게임만 먼저 보이고 나머지는 펼칩니다. 누르는 영역은 최소 44px, 결과 모달이 열렸을 때 같은 결과 카드를 뒤에 다시 보이지 않습니다.
- **접근성**: 이모지는 분위기를 보조할 뿐 이름을 대신하지 않습니다. 색만으로 상태를 구분하지 않고, 동작 줄이기·키보드 이동·명시적인 버튼 이름을 유지합니다.

문구를 추가할 때는 “사용자가 지금 무엇을 알았고, 다음에 무엇을 누를 수 있는가”를 한 번에 답하는지 확인합니다. 예: `지도를 쓸 수 없어요`에서 끝내지 않고 `다시 시도`와 `가게 목록 보기`를 함께 둡니다.

## 게임 설계 — 연출만 다르고 결과는 하나

`winnerIndex` 는 호출하는 쪽(`App.tsx` 의 `spin()`)이 `selectCandidates` + 균등 난수로 먼저 정합니다. 게임은 그 결과를 보여주기만 합니다. 게임이 결과를 계산하면 "최근 1주 제외" 의 공정성 근거가 무너지고 `selectCandidates` 의 테스트가 의미를 잃습니다.

연출이 정해진 결과에 도달하는 방법은 게임마다 아래처럼 갈립니다(돌림판·슬롯은 멈출 자리를 정해 돌리기만 합니다).

- **가린 칸에 놓기** (사다리·카드): 사용자가 고른 출발점·카드가 닿는 칸에 당첨을 놓고 나머지를 섞어 엽니다(`revealSlots`). 칸은 열릴 때까지 전부 가려져 있으므로 미리 섞어 숨긴 것과 확률이 같습니다.
- **이기는 대진표 만들기** (토너먼트): 당첨이 모든 경기를 이기도록 대진을 짜고, 대진 순서와 다른 경기 결과만 섞습니다(`lib/tournament.ts`). 시작 전 "응원" 은 결과와 무관합니다.
- **뒤집을 때 앞면 정하기** (짝 맞추기): 두 장씩 뒤집어 짝을 맞춘 가게는 탈락하고, 끝까지 남은 짝이 점심입니다. 카드 앞면은 뒤집는 순간 정합니다 — 당첨이 아닌 가게 장을 먼저 다 쓰고, 당첨 짝은 마지막까지 안 뒤집힌 두 장이 됩니다(`lib/memory.ts`). 안 뒤집힌 카드는 서로 구별되지 않으므로 기억력이 그대로 통합니다. "처음 맞춘 짝이 당첨" 규칙은 쓰지 않습니다 — 이미 본 두 장으로 아무 가게나 맞출 수 있어 당첨을 미리 정해 둘 수 없습니다. 사람이 직접 두는 판이라 길이가 정해져 있지 않아, 카드를 뒤집을 때마다 App 의 연출 잠금 상한(30초)을 다시 잽니다.
- **이름표 맞바꾸기** (핀볼): 물리를 한 번 실제로 돌리고, 1등한 구슬과 당첨 구슬의 이름표를 맞바꿉니다(`raceForWinner`). 구슬은 이름 말고 다른 점이 없어 맞바꾼 경기도 물리적으로 맞습니다. 예전엔 당첨이 이기는 시드를 찾을 때까지 경기를 돌렸는데, 판을 1840px 로 늘리자 후보 20곳에서 최악 7.9초 출발 게이트가 멈췄습니다.
- **경로 역산** (플링코): 오른쪽으로 꺾인 횟수가 곧 도착 칸입니다. 당첨 칸 번호만큼 "오른쪽" 을 넣은 좌/우 배열을 섞어 경로로 씁니다(`lib/plinko.ts`). 어느 순서든 같은 칸에 닿으므로 판마다 맞는 핀만 달라 보입니다.
- **거리 나누기** (주사위): 말이 있는 칸에서 당첨 칸까지의 거리를 1~6 눈 여섯 번 이하로 나누고, 마지막 눈에 정확히 닿게 합니다(`lib/dice.ts`). 같은 칸이면 한 바퀴 돕니다. 말은 지난 판 자리에서 출발하고, 가게는 둘레에 고르게 흩어 두며 사이 빈 칸도 한 칸씩 밟습니다 — 앞에서부터 채우면 후보 5곳일 때 아래·왼쪽 변이 통째로 비었습니다.
- **기록 맞바꾸기** (경마·레이싱): 주자마다 구간 속도와 사고(넘어짐·스핀)·부스트(당근·니트로)·휘청임을 무작위로 만든 뒤, 가장 빨리 들어온 기록을 통째로 당첨에게 줍니다(`lib/race.ts`). 둘 다 CSS perspective 로 눕힌 타원 트랙(`RaceCircuit.tsx`)을 달립니다 — 레이싱은 아스팔트 서킷(최대 6차선 점선, 차 색은 순번으로 갈라 겹치지 않음), 경마는 흙 주로(말은 판 기울기만큼 되세운 billboard)입니다. 바퀴 수는 1·3·5 중 고르고(기본 3, 게임별로 기억) 바퀴가 많으면 사건도 늘어납니다. 기록은 바퀴 수와 무관한 거리 0~1 이라 바퀴 수는 그리기·재생 시간만 바꿉니다. 핀볼처럼 "자리 섞기" 로 출발 차선을 섞을 수 있습니다(보이기만 바뀝니다). 두 게임 모두 관중이 트랙 밖에서 던진 것(바나나 껍질·음료수·기름통)이 포물선으로 날아와 주자 바로 앞에 떨어지고, 밟은 주자가 미끄러집니다(`slip`). 레이싱 사건은 부스터·타이어 펑크·전복이고, 전복은 그 순간 가장 가까이 붙은 차를 같이 받습니다(`collisions`, 앞 구간부터 처리해 실제로 붙어 있을 때만). 경마 사건은 한 마리당 둘까지이고 같은 종류도 두 장면 중 하나로 그립니다(넘어짐/기수 떨어질 뻔, 당근/채찍 질주, 풀 뜯기/뒤돌아보기, 부딪힘) — 말 머리 위 말풍선과 흙먼지. 말은 품종 여덟 가지(밤색말·얼룩말·흑마·백마·점박이말·팔로미노·회색 얼룩말·유니콘)를 순번으로 받고, 판마다 한 칸씩 돌려 가게가 적어도 판이 바뀌면 다른 말이 나옵니다. 순위표 이름을 누르면 카메라가 그 주자를 당겨 따라갑니다. 사고도 기록과 함께 옮겨 가서 당첨이 넘어졌다가 역전하기도 합니다. 2등 이하 순서와 선두 바뀜은 판마다 다르고, 테스트가 당첨 단독 1등·선두 교체 빈도·사고 빈도를 잡습니다.
- **당첨 자리에서 멈추기** (폭탄 돌리기): 폭탄이 지난 판 자리에서 출발해 두 바퀴·14걸음 이상 돌고, 마지막 걸음이 항상 당첨 자리에 닿도록 걸음 수를 정합니다. 자리마다 머무는 시간만 무작위이고, 뜸은 당첨 바로 앞 한 칸에서만 들입니다(`lib/bomb.ts`).
- **당첨만 남기기** (풍선 터뜨리기): 당첨이 아닌 풍선을 모두 정확히 한 번씩 터뜨리고 당첨 풍선은 터뜨리지 않습니다. 정하는 것은 터지는 순서와 간격뿐이라 마지막에 남는 풍선이 곧 당첨입니다(`lib/balloon.ts`).
- **마지막 입질이 당첨** (낚시): 몇 번의 입질은 모두 당첨이 아닌 물고기에게 주고, 마지막에 걸리는 물고기만 당첨으로 둡니다. 당첨이 먼저 다가왔다 떠나면 헷갈려서 앞 입질에서는 뺍니다(`lib/fishing.ts`).
- **구별 없는 캡슐** (뽑기 기계): 돔 안 캡슐에는 이름이 없고 서로 구별되지 않습니다. 어느 캡슐이 떨어지든 열면 당첨 가게입니다. 돔에는 20개까지만 그리고 나머지는 "…외 N개" 로 적습니다.

물리를 그냥 쓰면 안 되는 이유가 있습니다 — 구슬 레이스는 출발 위치와 판 모양 때문에 균등하지 않습니다. 핀을 한쪽으로만 엇갈리게 깔았을 때 오른쪽 끝 구슬이 600 시드 중 한 번도 못 이겼습니다. 지금 코스는 벽도 핀도 좌우 대칭이고, 대칭이 깨지면 테스트가 잡습니다.

핀볼은 긴 판(1840px, 1등 도착 평균 12~14초)을 카메라가 선두를 따라 내려갑니다. 공이나 오른쪽 순위판 이름을 누르면 카메라가 그 공을 따라가고(스포트라이트·머리 위 이름표·실시간 등수 배지), 그 공이 들어오면 몇 등인지 알려 줍니다. 배속은 `lib/pinballTiming.ts` 의 연속 곡선입니다 — 계단으로 바꾸면 "지연되다 갑자기 빨라짐" 으로 보입니다. 1등이 들어오면 0.7초만 더 보여 주고 끝냅니다. 나머지 구슬을 빨리감기로 마저 감던 꼬리는 결과만 늦춰서 뺍니다.

핀볼에는 판 테마가 넷 있습니다(기본·우주·정글·카지노, `lib/pinball.ts` `buildCourse(theme)`). 물리 규칙은 같고 코스와 장치만 다릅니다 — 블랙홀(가로로만 끌어당긴다), 웜홀(입구와 출구가 좌우로 엇갈린 한 쌍), 회전 고리(원을 도는 핀), 가속 구간(폭포)이 테마마다 섞입니다. 어느 테마든 출발과 깔때기·출구는 같고, 판은 좌우 대칭이며, 어떤 구슬 수에서도 전원 완주하는지 테스트가 지킵니다(`pinball.themes.test.ts`). 당첨은 테마와 무관합니다 — 이름표 맞바꾸기가 그대로입니다.

핀볼만 가게마다 공 개수(1~5개, 판 전체 36개까지)를 바꿀 수 있습니다. 공 개수는 확률입니다 — `spin()` 이 핀볼일 때 개수에 비례해 뽑고(`lib/weights.ts` `pickWeighted`), 핀볼은 그 가게 구슬 하나가 1등 하는 경기를 보여 줍니다. 전부 1개면 균등 추첨과 같은 결과를 냅니다(같은 난수 → 같은 당첨). 개수는 이번 방문 동안만 쓰고, 개수가 다르면 결과에 "공 8개 중 4개였어요 · 확률 50%" 를 남깁니다. 다른 게임은 늘 균등입니다. "자리 섞기" 는 게이트 줄만 섞습니다 — 출발할 때 구슬이 실제 출발 자리(시드로 섞인다)로 한 번 더 섞여 들어갑니다.

모든 게임에 "크게 보기"(`.stage--full`)가 있습니다. 핀볼은 이때 보이는 판 높이를 줄여 가까이 당겨 보여 줍니다.

짧은 게임도 끝나기 직전에 뜸을 들입니다. 사다리는 경로 마지막 20% 를 시간 35% 동안 천천히 내려가고(`ladderPace`, 끝은 1 이라 도착 칸 불변), 슬롯은 감속 꼬리를 길게 끌며 데스크톱에선 다섯 줄을 보여 줍니다. 카드는 섞은 뒤 고른 카드가 떠올라 떨리다가 뒤집히고, 토너먼트는 경기 승자가 튀어나옵니다.

CSS 연출은 `@media (prefers-reduced-motion)` 대신 `html[data-motion='reduced']` 를 따릅니다. 기기 설정이 "동작 줄이기" 여도 앱에서 "연출 켜기" 를 누르면 JS 연출과 CSS 연출이 같이 켜져야 해서입니다.

## 재미 요소 — 축하 연출 · 동료 예측 · 이번 달 기록, 당첨과 무관

셋 다 보여 주기만 하고 `spin()` 은 보지 않습니다. 당첨은 여전히 `selectCandidates` + 균등 난수입니다.

- **축하 연출**: 게임이 끝나 결과 모달이 처음 뜰 때 꽃가루가 터집니다("결과 보기" 로 다시 열 땐 안 터집니다). 소리는 기본 끔 — 사무실에서 갑자기 울리면 곤란합니다. 크게 보기 옆 "소리" 로 켠 사람만 효과음(Web Audio)과 휴대폰 진동을 받습니다. 동작 줄이기 기기에선 셋 다 없습니다.
- **동료 예측**: 게임 판 아래 한 줄. 링크로 들어온 사람이 이름과 가게를 찍으면 `predictions/{오늘}/votes/{익명 uid}` 에 쓰이고, 결과 티켓에 "🎯 맞힌 사람" 이 붙습니다. 기기당 하루 한 표, 자기 표만 쓰고 지웁니다(규칙 P1~P4). 게임 중엔 잠깁니다 — 결과를 보고 바꾸면 내기가 아닙니다.
- **이번 달 기록**: 목록 탭 맨 위. 횟수·자주 간 곳·뱃지 다섯(개척자·골고루·단골·꾸준함·점심 열 번). 방문 기록 31일치(`VISIT_HISTORY_DAYS`)에서 계산하므로 새 Firestore 읽기가 없습니다. 꾸준함은 기록 있는 평일이 이어진 날 수이고 주말은 건너뜁니다.

## 성능 — 게임 코드 나눠 받기 · 글꼴 비차단

Lighthouse 모바일(프로덕션 빌드)로 잽니다. 돌림판 말고 게임 14종은 고를 때 받고(`components/games/lazy.tsx`), 첫 화면을 그린 뒤 쉬는 시간에 미리 받아 둡니다. React.lazy 를 안 쓴 이유는 이미 받은 모듈도 첫 렌더에 한 번 멈추기 때문입니다. 10/13 기준 성능 74(FCP 2.7초, LCP 약 6초). 남은 무게는 Firestore·Auth SDK 이고, Archivo 글꼴은 MODUL `styles.css` 의 `@import` 라 앱에서 뺄 수 없습니다.

## 지도 탭 — SDK 동적 로드 · 라벨 핀 · 길게 눌러 가게 넣기

SDK 는 지도 탭에 처음 들어갈 때만 받습니다. 결정 화면 번들에 카카오가 들어가지 않는 것은 `pnpm build` 로 확인합니다(메인 번들에 `dapi.kakao` 0건).

성공이든 실패든 탭 진입당 스크립트 요청은 1회입니다. 실패도 캐시하고 "다시 시도" 를 눌렀을 때만 지웁니다 — 처음에는 실패한 약속만 버렸더니 탭을 오갈 때마다 401 이 새로 났습니다.

가게는 카카오 기본 마커 대신 카테고리 그림·이름·도보 분이 적힌 HTML 핀(`map/pin.ts`)으로 그립니다. 이름은 `textContent` 로만 넣습니다. 고른 핀은 반전되고 맨 위로, 오늘 정한 곳엔 별, 멀리 보면(배율 5 초과) 이름을 접습니다. 꺼 둔 가게 핀은 기본으로 숨기고 체크박스로 켭니다. 지도 위 카테고리 칩은 핀만 거릅니다 — 오늘 탭의 조건과는 따로입니다. 도보 원(5·10·15분)은 위쪽 끝에 "도보 N분" 라벨을 단습니다. 정해 둔 회사 위치 카드는 한 줄로 접혀 있고, "바꾸기" 로 펼쳤다가 "접기" 로 닫습니다.

지도를 **500ms 꾹 누르면** 그 자리에 핀이 꽂히고 저장 폼이 열립니다. 폼은 모달이 아니라 오른쪽 칸(휴대폰은 지도 아래)에 붙습니다 — 모달은 방금 찍은 자리를 가렸습니다. 10px 넘게 움직이면 지도를 끄는 것으로 보고 취소합니다. 이렇게 넣은 가게는 `kakaoPlaceId` 가 비어 있어서, 검색으로 넣은 가게와 중복 판정 방식이 다릅니다 — 이름이 같고 30m 안이면 같은 가게로 봅니다.

`map.relayout()` 을 `ResizeObserver` 로 계속 겁니다. 카카오는 만들 때의 컨테이너 크기를 기억해서, 그 뒤 폭이 바뀌면 타일이 예전 크기만큼만 깔립니다.

## 도보시간 — 직선거리 기반 추정과 교체 트리거

직선거리 × 1.3 ÷ 67m/분. 교체 트리거는 **시드 12곳 중 2곳 이상에서 실제 도보시간과 2분 넘게 차이** 이고, 판단은 직접 걸어보고 합니다. 그때 카카오 길찾기로 바꿉니다.

## 판정 기준 — 2주차 visits 8건

가동 2주차 끝에 누적 `visits` 가 8건 이상이면 계속, 3~7건이면 보류(3주차 단독 3건으로 재판정), 2건 이하면 중단합니다. 풀은 2주 안에 20곳을 넘겨야 최근 방문 제외가 자동 완화 없이 돌아갑니다.

제외 창은 7일입니다(`RECENT_WINDOW_DAYS`). 처음엔 14일이었는데 회사 근처 밥집이 적어 1주로 줄였습니다(10/13). 방문 기록은 그대로 14일치를 읽어(`VISIT_HISTORY_DAYS`) 목록 탭 "최근 다녀온 곳" 과 "다시 넣음" 순서가 1주 너머도 보입니다.
